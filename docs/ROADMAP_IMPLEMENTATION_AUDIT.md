## Verified current state

### Real-hot-deal acceptance contract

The live target counts only current, source-backed hot deals: future departure date, unexpired `valid_until`, `deal_score >= HOT_DEAL_SCORE` (default 80), `discount >= HOT_DEAL_DISCOUNT` (default 20), `confidence >= HOT_DEAL_CONFIDENCE` (default 0.65), and a non-null HTTPS Google Flights source URL generated from the observed route and dates. The scanner now carries this URL into `deals`; the live loop reports and gates on this qualified count rather than all published rows. A Google Flights URL is a source/search link and must not be described as proof that the observed fare remains bookable until the user verifies it on the provider page.

The launch scan coverage is configured for eight departure windows per enabled route (`7, 14, 30, 45, 60, 90, 180, 270` days) so the target represents distinct future travel times rather than repeated scans of one window. Migration `20260804000100_expand_hot_deal_scan_windows.sql` must be applied before live scanning; provider quota and route breadth remain runtime capacity constraints.

Migration `20260804000200_expand_launch_route_matrix.sql` adds source-backed route coverage across Hanoi, Ho Chi Minh City, Da Nang and Phu Quoc to major Asian, European, Middle Eastern and Oceanian destinations. The live scanner batches eight route groups and two offset groups across 16 cycles to avoid the Supabase worker resource limit observed with a 128-request invocation.

Migration `20260804000300_expand_long_horizon_scan_windows.sql` adds 15 distinct departure offsets through 365 days. The live loop uses four offset batches and eight route batches across 32 cycles; each invocation remains bounded while the resulting deals represent different future dates.

Migration `20260804000400_expand_secondary_origin_matrix.sql` adds CXR, VDO, HPH and VCA origin coverage. With 12 route batches and four offset batches, the next live sweep uses 48 bounded cycles.

The scanner now skips a route/date window when a fresh observation exists within `SCAN_CACHE_TTL_HOURS` (default 72); routes with existing hot evidence use the shorter `SCAN_HOT_ROUTE_CACHE_TTL_HOURS` (default 6). It records skipped windows in `scan_runs.response_payload` and succeeds on fully cached batches without spending provider searches.

The scanner now supports `FLIGHT_PROVIDER=amadeus` with `AMADEUS_CLIENT_ID`, `AMADEUS_CLIENT_SECRET`, `AMADEUS_BASE_URL` and `AMADEUS_CURRENCY`. Amadeus offers are normalized through the same validated contract as SerpApi; the provider is opt-in and fails closed when credentials are absent. No Amadeus credential is currently configured on the remote project, so this adapter is code-ready but not live-verified.

Migration `20260805000100_deal_snapshots.sql` adds immutable source-backed snapshots for each verified itinerary observation. `deals` remains the active/upserted feed; `deal_snapshots` is the historical hot-deal archive and never implies that an expired fare is still bookable.

`.github/workflows/real-data-pipeline.yml` now schedules one bounded adaptive batch every 12 hours and supports manual dispatch. It requires GitHub Actions secrets `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` and `INTERNAL_FUNCTION_SECRET`; provider credentials remain server-side Supabase secrets.
