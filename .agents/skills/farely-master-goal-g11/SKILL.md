## C3. Farely opportunity truth algebra — compile the FULL meaning

# 04. Long-horizon Antigravity executor design, not twenty research passes

At Goal startup the executor reads actual repo worktree, git status/branch/remotes, application architecture, existing tests, permissions, CI and run state. Plan compatibility, backfill/reconciliation, dual-read/write only if researched/approved, traffic/caller mapping, observation and rollback. # 05. Proof oracle, false-DONE resistance and terminal algebra

## Authority tiers
T0: executor text claim; T1: executor-controlled local test/screenshot; T2: independently rerunnable traces/logs and frozen expected values, subject to actual edit rights; T3: independently controlled protected CI/reviewer/production evidence when genuinely configured. An artifact's format never upgrades its trust. Never label T1 as T3 merely because it has a SHA or hash file stored in same editable repo.

## Per-CAP acceptance
Specify observed path, exact threshold/timezone/population from source (or explicitly unknown), positive + negative/fault/permission tests, error path, integrated user workflow, regression after shared changes, and evidence identity: source commit SHA, environment, test command/data/time, output location and tester/authority. Outcome windows requiring real users/time cannot be substituted with a demo; use `OUTCOME_PENDING` until observed.

## Hostile acceptance
Attempt to falsify alleged PASS: delete/mislabel P2/P3; keep CAP IDs but lower solution; keep GATE IDs but delete negative tests; shortcut mocked/demo-only path; swallow errors, empty datasets, fake metrics; move authority while old caller still runs; allow insecure permissions; mark blocker WAITING as PASS; report GitHub push unverified; stale commit/deploy proof; configure CI checks through an executor-editable gate.

## Evidence invalidation
Change to source/runtime env/tests/verification criteria/data shape/shared owner/DB migration may invalidate own and dependent proofs. Re-run affected gates after last material change. The same commit on local and remote is necessary for Git identity, not sufficient to prove deploy identity or product behavior.

## Separation of powers
Prefer baseline acceptance held outside executor-editable tree (branch rules, independent GitHub App status, review permissions, externally run outcome probes) if user already provided/authorized. Do NOT claim these controls exist just because Goal asks for them. If unavailable, disclose residual verifier-dependence and request independent acceptance; never claim protected/third-party T3.

## Terminal conjunction
`TARGET_PROVEN` only if (a) full selected REQUIRED P0–P3 roster preserved; (b) all per-CAP solution, real-path and negative gates ACCEPTED; (c) end-to-end whole-product outcomes and shared invariants proved; (d) required migration/cutover and regression pass; (e) every mandatory observation window has elapsed or is source-approved bounded; (f) evidence fresh for final tested SHA/env; (g) actual authorized GitHub push verified by remote ref and CI/deploy claims only when independently observed; (h) no open critical blocker, tampered oracle or unresolved selected decision. No additive score can cancel a failed hard gate.

Else use exact honest status: `IN_PROGRESS`, `REVISE`, `REGRESSION_FAIL`, `REVIEW_REQUIRED`, `OUTCOME_PENDING`, `RESOURCE_CHECKPOINT` or `HARD_BLOCKED`; report outstanding CAP and next action. Do not relabel failure to satisfy an arbitrary 100/100 score.

# 08. Concrete anti-bypass controls compiled into the Master Goal

Apply these as meaningful behavior/proof requirements, not merely keyword markers.
An executor controlled test is not independent. The source is Skill 1; this policy cannot override source-selected solutions.

## C01 — Handoff possession

**Normative rule:** Reject a READY title without full I-XIII and materially complete dossiers.

**Counterexample to reject:** Fake index-only packet or fabricated readiness.

## C02 — Bidirectional completeness

**Normative rule:** Compare source obligations to goal and goal additions back to source; orphan or missing CAP fails.

**Counterexample to reject:** Retain only the P0 hotfix while calling mission complete.

## C03 — P0 exactness

**Normative rule:** Preserve original P0 failures, hard gates, security and nonfunctional thresholds.

**Counterexample to reject:** P0 marked done by green compile without real failure probe.

## C04 — P1 full flows

**Normative rule:** Preserve every P1 required workflow and its real API/db effects.

**Counterexample to reject:** Demo workflow accepted despite missing live backend mutation.

## C05 — P2 same-mission coverage

**Normative rule:** Every selected REQUIRED P2 has implementation, integration, gate and wave in SAME Goal.

**Counterexample to reject:** Move P2 into a future prompt to close this goal.

## C06 — P3 same-mission coverage

**Normative rule:** Every selected REQUIRED P3 gets concrete user-facing path and independent-enough proof.

**Counterexample to reject:** Drop UX/accessibility/observability P3 after core tests pass.

## C07 — Conditional trigger isolation

**Normative rule:** Keep untriggered future capabilities designed but not falsely mandatory without observed trigger.

**Counterexample to reject:** Invent trigger or deploy speculative feature to prolong run.

## C08 — Supersession firewall

**Normative rule:** Do not resurrect rejected/obsolete architectures; preserve explicit exclusion evidence.

**Counterexample to reject:** Implement simpler deprecated queue despite locked decision.

## C09 — Solution semantics

**Normative rule:** Compare approved algorithm, schema, API/state ownership and thresholds, not matching SOL IDs only.

**Counterexample to reject:** Retain SOL-ID but substitute weaker implementation.

## C10 — Causal product path

**Normative rule:** Trace every root cause to selected mechanism to end-user outcome and observed effect.

**Counterexample to reject:** Code exists but neither caller nor user path uses it.

## C11 — Global invariants

**Normative rule:** Validate cross-domain authoritative data owner, security boundary and consistency end-to-end.

**Counterexample to reject:** Two writers both claim sole ownership under passing unit tests.

## C12 — Migration & cutover

**Normative rule:** Test data reconciliation, old-path retirement, rollback and actual traffic authority switch.

**Counterexample to reject:** New module passes tests while old worker handles production.

## C13 — Dependency closure

**Normative rule:** Check acyclic DAG with all required waves and cross-CAP regression prerequisites.

**Counterexample to reject:** Wave two skipped as blocked yet terminal still passes.

## C14 — Negative falsification

**Normative rule:** Use negative, retry, fault, permission and real browser/API/backend tests, not mock-only evidence.

**Counterexample to reject:** Screenshots and mocked status replace durable failure behavior.

## C15 — Oracle control

**Normative rule:** State whether acceptance test baseline and verifier are outside executor control; never claim T3 from self-edited CI.

**Counterexample to reject:** Agent edits tests/thresholds to certify itself.

## C16 — Evidence freshness

**Normative rule:** Invalidate affected proofs after source/config/test/dependency changes and tie them to final SHA/environment.

**Counterexample to reject:** Cached PASS from prior commit reused as final proof.

## C17 — Outcome observation

**Normative rule:** Preserve delayed real-product metrics and observation windows; use OUTCOME_PENDING when unobserved.

**Counterexample to reject:** Claim metric achieved without enough real users or elapsed time.

## C18 — Durable continuation

**Normative rule:** On quota/context/policy interruption checkpoint outstanding CAP/gates and resume instructions; no fake restart guarantee.

**Counterexample to reject:** Resource limit converted into done or silently discarded work.

## C19 — GitHub remote proof

**Normative rule:** Require normal authorized commit and push, remote SHA check, final tree reconciliation and observed CI/deployment claims.

**Counterexample to reject:** Git status or local commit misreported as GitHub push.

## C20 — Hostile terminal veto

**Normative rule:** Try a concrete counterexample for every terminal predicate; any unsatisfied hard gate forbids TARGET_PROVEN.

**Counterexample to reject:** Any one P3, cutover, outcome or remote proof absent but reported 100/100.

# 09. Semantic source-to-executor compilation (v9)

**Hard distinction:** an ID, keyword, digest or accepted synthetic JSON card never proves semantic equivalence. Semantic fidelity requires a *two-way argument* connecting each source decision to an executable implementation and a falsifiable real-world outcome. Treat automatic field matching as a cheap early warning, never as a certification.

## Atomize ONLY what survives research

Read actual Sections I–XIII of the full Skill 1 v9 report. Make internal **obligation atoms** from each required CAP and selected shared/global invariant. An atom contains:

- `ATOM-ID`, source span/section (I–XI), `CAP-ID`, `P0..P3`, `REQUIRED_IN_MASTER_GOAL`, original outcome and root cause;
- exact selected `DEC-ID`/`SOL-ID`, mechanism, data/state/interfaces/API/schema/algorithm, unit+threshold, exception and recovery;
- concrete implementation side effect and actual path of invocation, integration dependencies and cutover/rollback;
- positive and negative counterexample, required proof modality, proof owner/trust tier, time window/environment, blast radius and obligations invalidated by change;
- superseded alternative exclusion or conditional trigger when relevant.

Verify the complete causal loop: root cause → selected engineering mechanism → observable end-user behavior → measured product outcome → falsification test. A code diff alone is not causal proof.

One capability often contains multiple atoms (schema uniqueness, consumer use, failure case, and reconciliation). **Never count a single CAP card as full coverage when atoms are missing.** Do not invent numeric thresholds or undocumented implementation files; unresolved consequential data blocks compilation.

## Internal compilation witness

Create a conceptual matrix `ATOM-ID → exact Goal section/card/span → executor action → oracle expectation → evidence slot → repair route → terminal gate`. For every required ATOM, every column must be filled with actionable content. For every emitted task, reverse-map it to an authorized atom, required supporting infrastructure or safety mechanism. Reject mystery tasks, overbuild for duration, and unverifiable "best practice" filler. A shared subsystem may serve several CAPs, but each CAP's acceptance remains individual and cross-product integration must be tested.

The following are **non-substitutable**: an `implemented` marker cannot replace a user journey; a unit test cannot replace E2E or observed outcome; a screenshot cannot replace authenticated write/readback; local git commit cannot replace observed remote SHA; executor-edited CI cannot replace an independent protected oracle; a "could be improved later" P2/P3 note cannot replace an implementation obligation in the same Goal.

## Decision closure and supersession

Only final decisions still supported by latest user/Skill 1 authority may appear as recommended build paths. Keep rejected and superseded mechanisms in a *do-not-reintroduce* list, not as live option menus. Unknown current file paths may be checked by executor under a **bounded discovery branch**. If discovery falsifies a root design premise, stop only that branch, preserve other ready work, report exact evidence and request research/owner approval; never silently substitute a new architecture.

## Meaning-preservation audit after M20

Independently re-read source **without reading the candidate Goal**, reconstruct required atoms and priorities including P2/P3, then compare with final compiled Goal: missing, added, weakened, wrong order, wrong gate, wrong proof tier, wrong source authority, inherited stale SHA, wrong conditional treatment and orphaned global invariants. A small compiler index is not a substitute for full details inside the one-fence Goal. If detailed transmission is impossible, return OUTPUT_CAPACITY_BLOCKED honestly.

# 10. Trust boundary and falsifiable acceptance (v9)

## The attacker's capabilities are the executor's edit permissions

Assume an eager executor may (accidentally or strategically) remove P3, relabel P2, weaken thresholds, replace real services with stubs, edit the unit test, invert a failing exit code, delete negative cases, change fixture truth, ignore downstream consumers, create stale CI proof or claim push success after terminal denial. Assume an honest executor can still make the same mistakes. Threat-model these behaviors as **counterexamples to build quality**, not malicious-user instructions.

Never claim prompt-only protection. Distinguish:

- `T0`: executor narrative/checklist claim; informative only.
- `T1`: logs/tests produced and fully controlled by executor; reproducible if files survive, not independent.
- `T2`: results reproducible by reviewer from actual code, logs and current environment against known criteria; author/source of oracle must be stated.
- `T3`: independently controlled/immutable outside executor permissions, e.g. authorized reviewer-run hidden E2E, protected CI workflow/status source, external analytics readback. `T3` requires a real external boundary, not the phrase "independent QA".

**No independent oracle → no independent PASS claim.** If source requires T3 and no reviewer/source exists, status `REVIEW_REQUIRED` until real T3; do not have agent counterfeit it. Request human approval only for a truly required privileged action, while progressing other authorized tasks.

## Authority and baseline

The Skill 2 Goal delivered in the user's message is the reference mission contract. In the executor, create a project-local *working mirror* of roster/gates (permitted) for checkpoints. Executor ownership of that mirror does **not** make it immutable. A hash generated, updated and verified by the executor alone proves only consistency of its own claims. Use out-of-band comparison to the original user-supplied Goal, plus protected branch/ruleset / externally held tests when configured.

Never instruct enabling indiscriminate shell/network privileges to force progress. Antigravity `Deny/Ask/Allow` is enforced by the platform. Use authenticated, authorized branch and actual credentialed network only when available. Do not turn missing permissions into false completion.

## GitHub chain-of-custody

At beginning: inspect `git status`, branch, remote, uncommitted user work, CI config and permission boundary. At safe checkpoints, commit/push authorized nonsecret progress with clear `INCOMPLETE` state to allow inspection; no claim of closure. For terminal closure:

1. Freeze final candidate code/config/test revision, record full SHA and worktree cleanliness (respect user's preexisting uncommitted changes; do not overwrite them).
2. Execute required gates on that revision and the correct environment; collect commands, timestamp, logs, data scope, SHA, verifier, CI/deploy IDs. If tested working tree differs from pushed tree, invalidate and retest.
3. Create normal commit and push to authorized feature branch. Obtain remote ref identity from actual authenticated `git ls-remote`/GitHub response and compare exact SHA. If PR/CI status is required, obtain check status for that SHA from authorized provider, not echo/text.
4. If app deployment is required, compare deployed build digest and environment with commit/artefact tested; local/remote SHA alone cannot prove runtime deployment.
5. On any last change affecting a gate, invalidate dependent proofs and replay verification. Never rewrite a protected branch, bypass review, force push or leak secrets.

Version equality, CI success and deployment identity are **necessary when demanded but do not guarantee product correctness**. An external reviewer must still validate high-consequence outcomes.

## Counterexample probes

Mandatory negative/fault paths by applicability: auth/session expiry, permission refusal, empty dataset, partial failure, retry/duplicate/reordered events, kill/restart, data loss and reconciliation, concurrent state writers, rollback, degraded network, stale cache, invalid request, local vs production-equivalent path, and system-level outcome. Define exact expected observable invariant for each chosen probe.

# 11. One Goal as a durable multi-wave execution program (v9)

## Initializer phase in SAME Goal

The executor must inventory actual repository state, map user-provided CAP roster and atomic obligations into a project-local `mission_state` with dependencies, evidence slots and current Git references; verify current service/build can start, record baseline outcomes before risky changes, and identify external blockers. This is an *implementation artifact*, not a Skill 2-created file. Never automatically mark legacy capabilities PASS on initialization.

## One mission, many waves

All P0–P3 with `REQUIRED_IN_MASTER_GOAL` are mandatory in one Goal. Waves order work by dependency, risk and cutover safety; **wave complete is not Goal complete**. Nontriggered future conditional requirements preserve research branch/trigger/owner without becoming endless required work. When source-approved condition activates, append activated obligations and retest dependent global gates. The P3 feature may never be silently relabeled optional merely to close.

Per CAP: source evidence → chosen solution → implementation changes → integration/caller switch → negative/fault/positive/E2E probes → regression → proof record → ACCEPTED if applicable. `IMPLEMENTED`, `VERIFIED`, `ACCEPTED` have strict semantics and distinct evidence tiers. Shared changes produce *proof invalidation edges*, not just work dependency edges: data schema or routing changes invalidate dependent CAP validation even when their files did not change.

## State / interruption

Canonical states: `NOT_STARTED`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFIED`, `ACCEPTED`, `REVISE`, `REGRESSION_FAIL`, `REVIEW_REQUIRED`, `OUTCOME_PENDING`, `RESOURCE_CHECKPOINT`, `HARD_BLOCKED`. `TARGET_PROVEN` is a derived program-level status, not a mutable status selected by the agent. After resource/context interruption, preserve open atom IDs, next executable tasks, exact commands, known failures, proof invalidation graph, branch/SHA, owner approvals and reentry verification. An interrupted run **cannot** claim it will automatically resume unless a real scheduler/supervisor exists and its behavior is verified.

Avoid deterministic infinite loops on an intrinsically blocked external dependency. Continue every independent ready workstream; for external-only blocker, make a faithful checkpoint and expose its human action. Long execution is a consequence of real work; neither extra fake features nor redundant empty verification rounds improve quality.

## Terminal conjunction

`TARGET_PROVEN` is permitted ONLY if:

- Full required P0–P3 atom roster from user-held contract is preserved and all per-CAP `ACCEPTED` gates have proof meeting their specified tier.
- All global invariants, end-user journeys, negative tests, data reconciliation, rollback and cross-CAP integration satisfy source thresholds.
- All material cutovers are truly in use; abandoned old callers/writers do not remain authoritative; migration proof has not expired.
- Required observation windows are complete with measured outcomes; no self-certified `OUTCOME_PENDING` substitutions.
- All evidence is fresh for source SHA and correct runtime/deploy environment; no critical failing checks or unresolved gate tampering.
- Authorized GitHub commit and observed push remote SHA match final tested revision; required external CI/deploy observations refer to same target identity.
- Protected independent gate is observed wherever source requires it; no open blocker, review wait or unknown that makes the acceptance logically unproven.

No percentage score, green dashboard, passing unit tests, Walkthrough or time elapsed may override a failed conjunct. A status report says exactly which atom/gate is not proven and the next safe action. If a source-goal conflict requires human authorization, do not quietly change the source contract.

## Safe stopping

Use `RESOURCE_CHECKPOINT` for quota/session, `REVIEW_REQUIRED` for permission/external verification, `OUTCOME_PENDING` for time/real users, `HARD_BLOCKED` only for genuine hard unsolvable blocker, `REVISE` or `REGRESSION_FAIL` for failures. On stopping, push safe nonsecret checkpoint work if authorized and verifiably possible; push failure is explicitly open. No misleading "DONE" header in a partial terminal report.
